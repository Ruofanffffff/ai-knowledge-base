However, the user reports it's still incorrect. This is likely due to a time zone mismatch or a logic error in `formatTimeAgo` combined with how `last_viewed_at` is stored.

**Investigation:**

1.  **Backend (`server.js`)**:
    *   `last_viewed_at` is updated using `CURRENT_TIMESTAMP` in SQLite. SQLite `CURRENT_TIMESTAMP` is in UTC.
    *   The returned JSON has `lastViewedAt` as a UTC string (e.g., "2023-10-27 10:00:00").

2.  **Frontend (`Dashboard.tsx`)**:
    *   Uses `formatTimeAgo(doc.lastViewedAt || ...)` to display the time.

3.  **Frontend (`utils/transformers.ts`)**:
    *   `formatTimeAgo` creates a Date object: `const date = new Date(dateString);`.
    *   If `dateString` is "2023-10-27 10:00:00" (from SQLite, no 'Z'), browsers might interpret this as *local time* or *UTC* inconsistently depending on the format.
    *   Specifically, `new Date("2023-10-27 10:00:00")` in Chrome/V8 often treats it as local time, whereas the DB stored it as UTC.
    *   If the user is in China (GMT+8), "10:00 UTC" stored in DB might be read as "10:00 Local", which is 8 hours behind the actual time "18:00 Local".
    *   Or, if `new Date()` treats it as UTC but the format is ambiguous, it might be off.

**Fix:**
I need to ensure the timestamp from the backend is treated as UTC.
In `server.js`, I should probably append 'Z' if it's missing, or better yet, `formatTimeAgo` should handle the timezone conversion robustly.
