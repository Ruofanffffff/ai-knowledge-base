# Requirements: Anchor-Driven Entity Synthesis

## Overview

实现基于锚点指纹的实体合成机制，确保知识图谱是"schema在同一语义锚点上的持续重叠"，而非简单的schema集合。这是知识图谱构建的核心架构修正。

## Problem Statement

当前系统存在架构偏差：
- ❌ Schema实例直接变成实体，缺少锚点合并步骤
- ❌ 实体合并基于名称相似度，而非语义锚点
- ❌ 缺少锚点指纹生成机制
- ❌ 图的生成逻辑不正确：schema本身不应生成图节点

正确的理念：
- ✅ Schema输出结构化实例（中间层）
- ✅ 锚点指纹判断"是不是同一个东西"
- ✅ 不同schema在同一锚点上重叠，才生成实体（图节点）
- ✅ 图是锚点重叠的结果，不是schema的集合

## User Stories

### 1. Schema实例生成
**作为** 系统开发者  
**我想要** Schema匹配后生成结构化实例（而非直接生成实体）  
**以便** 在锚点层面进行合并判断

**验收标准**:
- [ ] 1.1 Schema匹配成功后，生成SchemaInstance对象
- [ ] 1.2 SchemaInstance包含：schema名称、字段、置信度、支撑CKB
- [ ] 1.3 SchemaInstance不直接存储到数据库
- [ ] 1.4 SchemaInstance作为中间数据结构传递给锚点生成器

### 2. 锚点指纹生成
**作为** 系统开发者  
**我想要** 为每个Schema实例生成标准化的锚点指纹  
**以便** 判断不同schema实例是否指向同一实体

**验收标准**:
- [ ] 2.1 根据Schema定义的anchor_fields生成锚点指纹
- [ ] 2.2 锚点指纹格式：`{entity_type}|{normalized_field1}|{normalized_field2}|...`
- [ ] 2.3 字段值标准化：时间归一化（月份）、地点标准化、指标标准化
- [ ] 2.4 相同锚点指纹的实例必须指向同一实体
- [ ] 2.5 不同锚点指纹的实例必须是不同实体

### 3. Schema定义扩展
**作为** Schema设计者  
**我想要** 在Schema中定义anchor_fields  
**以便** 系统知道用哪些字段生成锚点指纹

**验收标准**:
- [ ] 3.1 Schema模型增加anchor_fields配置
- [ ] 3.2 anchor_fields指定用于锚点生成的字段列表
- [ ] 3.3 anchor_fields支持字段权重（可选）
- [ ] 3.4 anchor_fields支持标准化策略配置
- [ ] 3.5 现有250个Schema需要配置anchor_fields

### 4. 基于锚点的实体合并
**作为** 系统开发者  
**我想要** 将相同锚点的Schema实例合并为单一实体  
**以便** 实现"schema在锚点上重叠生成图"的设计

**验收标准**:
- [ ] 4.1 按锚点指纹对Schema实例分组
- [ ] 4.2 同一锚点的所有实例合并为一个实体
- [ ] 4.3 实体包含所有支撑的schema列表
- [ ] 4.4 实体字段合并策略：优先高置信度值
- [ ] 4.5 实体置信度基于支撑schema数量和质量
- [ ] 4.6 实体的supported_by包含所有相关CKB

### 5. 锚点冲突检测
**作为** 系统开发者  
**我想要** 检测锚点指纹相同但语义可能不同的情况  
**以便** 避免错误合并

**验收标准**:
- [ ] 5.1 检测同一锚点下schema实例的语义一致性
- [ ] 5.2 时间策略一致性检查（同月、同年等）
- [ ] 5.3 字段值冲突检测（数值差异、状态矛盾等）
- [ ] 5.4 LLM辅助判断是否需要拆分（建议模式）
- [ ] 5.5 记录冲突日志供人工审核

### 6. LLM参与边界
**作为** 系统架构师  
**我想要** 明确LLM的参与点和禁区  
**以便** 保持系统的确定性和可控性

**验收标准**:
- [ ] 6.1 ❌ LLM不参与：锚点指纹生成
- [ ] 6.2 ❌ LLM不参与：实体是否存在的最终裁决
- [ ] 6.3 ❌ LLM不参与：Schema定义本身
- [ ] 6.4 ✅ LLM参与：实体合并校正建议（是否误合并）
- [ ] 6.5 ✅ LLM参与：字段冲突裁决（兜底）
- [ ] 6.6 ✅ LLM参与：关系合理性校验
- [ ] 6.7 ✅ LLM参与：实体描述增强
- [ ] 6.8 所有LLM输出必须是"建议"而非"决策"

### 7. 管线集成
**作为** 系统开发者  
**我想要** 将锚点驱动机制集成到现有管线  
**以便** 替换当前的实体生成逻辑

**验收标准**:
- [ ] 7.1 修改universal_document_pipeline的实体构建步骤
- [ ] 7.2 Schema匹配后生成SchemaInstance列表
- [ ] 7.3 调用锚点生成器为每个实例生成指纹
- [ ] 7.4 调用锚点合并器生成最终实体列表
- [ ] 7.5 实体存储前进行冲突检测
- [ ] 7.6 保持向后兼容（可配置开关）

### 8. 数据模型更新
**作为** 数据库设计者  
**我想要** 更新实体数据模型以支持锚点机制  
**以便** 存储和查询锚点相关信息

**验收标准**:
- [ ] 8.1 Entity表增加anchor_fingerprint字段
- [ ] 8.2 Entity表增加anchor_fields字段（JSON）
- [ ] 8.3 Entity表的schemas字段存储多个schema信息
- [ ] 8.4 创建anchor_fingerprint索引以优化查询
- [ ] 8.5 支持按锚点查询实体
- [ ] 8.6 数据库迁移脚本

### 9. 测试覆盖

**验收标准**:

### 10. 文档和示例
**作为** 系统使用者  
**我想要** 清晰的文档和示例  
**以便** 理解和使用锚点机制

**验收标准**:
- [ ] 10.1 架构文档：锚点驱动设计理念

## Non-Functional Requirements

### 性能要求
- 锚点指纹生成：< 10ms per instance
- 锚点合并：< 100ms for 1000 instances
- 不增加整体管线处理时间 > 5%

### 可靠性要求
- 锚点指纹生成必须是确定性的（相同输入→相同输出）
- 合并逻辑必须是幂等的（多次执行结果一致）
- 系统崩溃后可恢复（中间状态可追溯）

### 可维护性要求
- 锚点配置与Schema定义分离
- 支持热更新anchor_fields配置
- 详细的调试日志

### 兼容性要求
- 向后兼容现有实体数据
- 支持渐进式迁移
- 可配置开关（新旧机制切换）

## Success Metrics

1. **正确性指标**
   - 相同语义实体的合并率 > 95%
   - 错误合并率 < 2%
   - 锚点指纹冲突率 < 1%

2. **性能指标**
   - 实体生成速度提升 > 20%（减少重复判断）
   - Token消耗减少 > 30%（减少LLM消歧调用）

3. **质量指标**
   - 实体置信度平均提升 > 10%（多schema支撑）
   - 图谱密度提升 > 15%（更多关系）

## Out of Scope

以下内容不在本次实现范围内：
- 跨文档的实体链接（后续feature）
- 实体演化追踪（后续feature）
- 锚点指纹的语义向量化（后续优化）
- 分布式锚点合并（后续扩展）

## Dependencies

- Schema定义系统（需要扩展）
- 字段标准化模块（需要增强）
- 实体存储模块（需要更新）
- Universal Document Pipeline（需要集成）

## Risks and Mitigations

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 锚点配置错误导致过度合并 | 高 | 提供配置验证工具、详细文档、示例 |
| 现有数据迁移复杂 | 中 | 提供迁移脚本、支持双模式运行 |
| 性能下降 | 中 | 性能测试、优化算法、缓存机制 |
| LLM边界不清晰 | 高 | 明确文档、代码注释、审查机制 |
